# Solana path for Boid's narrow MVP

Researched 2026-09-27 from first-party Solana and Anchor documentation. This is a planning note, not a security review.

## Recommendation

Prove `repo → economic model → strategy finding` before writing chain code. For the final demo, support one **USDC-style SPL token payment split with an optional referral reward**. Generate a parameterized, reviewable Anchor program patch or template for that one mechanism, plus tests. Use a locally minted six-decimal SPL token in tests and label it as a test asset; do not claim it is issuer-backed USDC. Solana's Token Program already supports minting, token accounts, and transfers, so a new token is unnecessary for a payment-split demo. [SPL Token Basics](https://solana.com/docs/tokens/basics), [SPL Token CLI reference](https://solana.com/docs/references/spl-token-cli)

If the flow only requires a buyer-authorized one-time split, the generated client could construct multiple ordinary token transfers. A custom program becomes justified when the split or eligibility must be enforced atomically onchain, or funds must be held pending release. Solana programs can invoke the Token Program through a CPI; `TransferChecked` verifies mint and decimals. A PDA can act as the authority for a program-controlled token account and sign a CPI with its seeds. This makes a minimal escrow or rule-enforced payout feasible. [Token CPI](https://solana.com/docs/tokens/advanced/cpi), [PDAs](https://solana.com/docs/core/pda), [Anchor transfer guide](https://www.anchor-lang.com/docs/tokens/basics/transfer-tokens)

## Minimal onchain contract shape

For a selected fixed-rate split, the generated program can expose `initialize_config`, `deposit` (only if escrow is needed), and `settle` or `release`. The config should bind the allowed mint, recipients/roles, fee and reward basis points, authority, and a version or immutable mechanism hash. Settlement uses checked integer arithmetic in token base units and verifies that all source and destination token accounts have the expected mint and owner. The sum of outputs must equal the input; specify a deterministic remainder recipient. These are **design recommendations** inferred from the Token Program's account and CPI rules, not built-in Anchor behavior. [Token accounts](https://solana.com/docs/tokens/basics), [Token CPI](https://solana.com/docs/tokens/advanced/cpi), [Verify token destination](https://solana.com/docs/payments/send-payments/verify-address)

For escrow, make a PDA the vault token-account authority, store deal state, and allow withdrawal only after an explicit condition. The condition must have a credible onchain proof or a clearly identified trusted signer/oracle; arbitrary offchain facts cannot be verified by the program merely because Boid modeled them. Anchor publishes an escrow example and PDA constraints, but Boid should implement only its own constrained settlement flow after its trust boundary is specified. [Anchor example programs](https://www.anchor-lang.com/docs/references/examples), [Anchor PDA constraints](https://www.anchor-lang.com/docs/basics/pda), [Token CPI](https://solana.com/docs/tokens/advanced/cpi)

Referral payouts are technically straightforward token transfers once an eligible referrer is established. The hard part is **proving eligibility and resisting self-referral/Sybil behavior**. A wallet address alone does not prove an independent person. Keep this as an explicit assumption or require a named eligibility authority; do not present an onchain referral transfer as a Sybil defense. This conclusion is an inference from the fact that Token Program transfers authorize token movement, while the referral relationship is application-specific. [SPL Token Basics](https://solana.com/docs/tokens/basics), [Token CPI](https://solana.com/docs/tokens/advanced/cpi)

## Framework and testing

Anchor is the practical MVP choice if Boid needs a custom program: it provides account constraints, PDA handling, IDLs, and a documented `transfer_checked` CPI pattern. This is a project recommendation, not a claim that Anchor is the only viable framework. Pin the CLI and library versions together and confirm compatibility before work starts; Anchor's current CLI documentation notes test-tool requirements for its default build architecture. [Anchor PDA constraints](https://www.anchor-lang.com/docs/basics/pda), [Anchor token transfer](https://www.anchor-lang.com/docs/tokens/basics/transfer-tokens), [Anchor CLI](https://www.anchor-lang.com/docs/references/cli)

Test the generated program's economic invariants with the same cases as the offchain engine: correct distribution, rounding, wrong mint, wrong authority, duplicate settlement, insufficient funds, invalid referrer, and boundary basis points. Use deterministic local tests; Anchor documents `anchor test` on localnet, and LiteSVM is an in-process option for fast program tests. Run at least one `solana-test-validator` integration path if the demo exercises RPC or wallet behavior, because LiteSVM does not reproduce every validator/RPC detail. No mainnet deployment is required for the technical proof. [Anchor local development](https://www.anchor-lang.com/docs/quickstart/local), [Anchor LiteSVM](https://www.anchor-lang.com/docs/testing/litesvm), [Anchor CLI](https://www.anchor-lang.com/docs/references/cli)

## Safe generation boundary

Generate **one known mechanism family** from a validated IR and emit source plus test fixtures for developer review. Do not let an LLM invent arithmetic, authorities, PDA seeds, or settlement conditions. The deterministic generator should map verified parameters into a fixed template; the LLM may explain the patch and identify integration points. Keep deployment a separate explicit step after review and tests. This is a Boid architecture recommendation based on the security-sensitive account authority and CPI mechanics described above. [Token CPI](https://solana.com/docs/tokens/advanced/cpi), [Anchor PDA constraints](https://www.anchor-lang.com/docs/basics/pda), [Solana deploying programs](https://solana.com/docs/programs/deploying)

## Cheapest falsification experiment

Hand-author one tiny Anchor split/escrow fixture matching the chosen IR, then generate only its rate and recipient configuration from the IR. Run the same transaction cases through the Boid deterministic transition engine and local program tests. If results diverge, or the app's desired referral eligibility needs unverifiable offchain facts, narrow the generated artifact to a client-side transaction plan or a reviewed integration sketch. This is a proposed experiment, not a finding from the sources.
